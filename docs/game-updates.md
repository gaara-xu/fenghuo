# 后台一键更新游戏

服务器源码目录：`/gaara/fenghuo`。后台 `/admin#update` 的“更新游戏”按钮会自行检查版本、拉取代码、准备依赖、编译测试、切换并重启游戏，无须先点检查，无二次确认，无须SSH或输入数据库参数。不内置定时更新。

按本轮要求，**更新按钮不备份、不迁移、不重置数据库**，不运行 `db:update` 或种子脚本。涉及数据库的后续功能必须在开发交付时另行同步数据库；程序版本回退不等于数据库回退。

## 首次启用

旧容器没有更新进程和持久化挂载，因此需要用本版本启动一次。110上已有克隆目录且无本地改动时：

```bash
cd /gaara/fenghuo && git pull --ff-only && bash deploy.sh
```

以后进入 `http://192.168.3.110:5173/admin#update`，直接点“更新游戏”。首次 `deploy.sh` 仍保留原部署脚本的既有数据库增量更新步骤；它不是更新按钮的执行流程。若仅更新代码不部署，当前服务器不会凭空增加挂载或更新能力。

### 已部署服务器修复更新器（运行协议3）

2026-09-29 修复检查更新长时间等待，以及 Git 大文件传输的 HTTP/2 framing / GnuTLS 中断。版本查询改用 GitHub API，源码改用 GitHub codeload 的固定提交源码包，由 Node HTTPS 下载，不再通过 Git/libcurl 拉取线上源码。不需要 SSH 密钥、不修改主机 Git 全局配置、不关闭证书校验。更新器固化在镜像中，单纯点击旧版更新按钮或拉源码不会替换它，需要在110执行一次：

```bash
cd /gaara/fenghuo && git pull --ff-only origin main && bash deploy.sh update-runtime
```

`update-runtime` 复用现有 `.env.docker` 和目录，先构建与测试，通过后再停止旧容器、激活新镜像代码并健康启动；不运行 `docker-db`、数据库检查／迁移／种子／备份／清理脚本。游戏正常启动仍会连接现有存档。构建失败不会停止旧游戏。它不是初始化部署入口，没有既有配置时拒绝执行。执行后恢复日常后台一键更新，无须每次运行本命令。

首次镜像准备需要 Node 22基础镜像、Debian软件源（Git、证书和文件锁工具）以及npm依赖下载可用；这些也可在能联网的机器构建成完整镜像后离线导入。服务器有Node基础镜像不等于已有这些工具和依赖。日常更新只需要访问GitHub；依赖锁改变时还需要npm下载通道，没有网络则明确失败、继续使用旧版，不切换半成品。

## 挂载和进程

- `/gaara/fenghuo` → 容器 `/source`，只读，保护原始源码、配置和原 `.git`。
- `/gaara/fenghuo/.game-update` → 容器 `/state`，保存独立Git仓库、完整版本、npm缓存及状态，可写；不提交Git、不进入镜像。
- 镜像自带Git、完整Linux编译依赖与一个可启动的初始游戏版本。
- 更新监督进程监听容器18770，对外仍为5173；游戏子进程仅监听容器回环18771，不额外开放端口。
- 游戏停止切换时，更新状态API和后台静态页面仍由监督进程提供；成功后已打开的更新页自动刷新新版资源。
- 文件锁防止两个监督进程同时使用同一更新存储。更新程序不挂Docker socket，不需要宿主机Node或执行任意宿主机命令。

日常更新拉取到 `.game-update/releases/<提交SHA>`，**不原地修改 `/gaara/fenghuo` 的工作树**，避免你本地改动、更新脚本自身和正在运行文件互相冲突。原目录的 `git log` 不是当前运行版本；当前版本以后台或 `/api/admin/game-update/status` 为准。

若之后手工拉取源码并再次执行 `bash deploy.sh`，完整部署会选用本次新镜像内的代码，不继续误用旧的已激活版本；已有版本目录保留供检查。

## 更新边界与失败处理

固定来源为 `https://github.com/gaara-xu/fenghuo.git` 的 `main`。通过 `api.github.com/repos/gaara-xu/fenghuo/git/ref/heads/main` 查提交SHA，再从 `codeload.github.com/gaara-xu/fenghuo/tar.gz/<SHA>` 下载该固定提交；不跟随重定向，不接受HTTP传入的仓库、分支、脚本、目录或命令。解压前完整检查 tar 头校验和、提交标记、固定根目录、大小上限和必要文件；禁止软／硬链接、特殊文件、路径覆盖扩展、重复条目、真实环境文件、路径穿越或预置 `node_modules`。`.env.example`仅作为模板允许。流式下载与解压不把大型素材包一次性载入内存，失败清理本次临时文件。

依赖锁与镜像一致时，复制匹配的Linux依赖到新版独立目录；不共用可被安装过程覆盖的运行目录。锁改变时在新目录 `npm ci --include=dev`，随后 `npm run check`。构建不继承数据库凭据，实库测试开关固定关闭。候选代码仍属于受信任的程序代码，因此GitHub仓库写权限必须只交给可信人员。

拉取、依赖安装、类型检查、单元测试或编译失败：旧游戏不停止。全部成功后，旧进程先停止接收请求并等待后台结算结束，再启动新版；不得双进程同时运行同一单人存档。启动健康检查包含目标版本标识，避免误把旧服务当成新版。

新版启动失败：停止候选进程，重新激活并启动原版；若原版也无法启动，保留管理更新页并明确显示失败。切换中断后重启：优先恢复切换前已确认版本，不把尚未健康确认的版本当成功。源码拉取、构建和进程健康检查有超时限制。

线上检查版本每次最多8秒，临时网络错误只重试一次，间隔0.5秒；不再回退到长时间 Git 等待。下载每次最多120秒，同样最多两次，并持续显示已下载大小。认证、证书、仓库不存在、源码安全校验失败不盲目重试。失败在更新页保留原因并释放忙碌状态，旧游戏继续运行；不把获取版本号成功误报成下载或更新成功。Git 通路只保留给本地测试仓库，不作为线上检查或下载的后备等待。

服务器受理完整更新请求后，更新任务独立于网页连接。关闭页面只停止浏览器轮询，重新进入继续读取服务器状态；单次网页请求超过10秒会退出等待并重新连接，不永久卡在加载中。迟到的旧进度不会覆盖较新的终态。停止容器会取消 Git／构建及重试等待，先向该命令的进程组发送SIGTERM，必要时SIGKILL，避免孤立子进程继续占用资源。

仅保留当前与上一个已构建版本；更新步骤最多保留24条，状态在文件中，不建数据库表。npm缓存、Git对象保存在上述专用目录。切换会短暂中断游戏请求；行军按既有离线逻辑继续结算。酒馆关闭记录模式的未领取内存候选在游戏进程重启后丢失，已入包物品不受影响。

`game-runtime.json` 声明运行协议和Node主版本。普通前后端源码、素材和npm依赖更新不重建镜像；Node、系统软件或监督进程协议变化需要更新固定镜像。监督进程来自镜像，不能靠覆盖正在运行的控制程序来冒险自升级。

## 接口

- `GET /api/admin/game-update/status`：只读状态，不检查远程、不更新。
- `POST /api/admin/game-update/check`：只检查版本。
- `POST /api/admin/game-update/run`：完整一键更新。

POST要求同源请求、`Content-Type: application/json`、`X-Fenghuo-Update: 1`，正文只有`requestId`。GET/HEAD不触发更新；明确预取、跨站请求拒绝。重复编号和更新进行中的点击不会并发执行。网页后台仍无用户登录，仅供受信内网使用。

本地开发或未安装监督进程的旧启动方式会返回“不支持一键更新”的明确状态，不会在开发电脑上拉代码、运行部署或重启服务。
